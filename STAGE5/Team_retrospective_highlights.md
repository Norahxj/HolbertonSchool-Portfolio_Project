## What Worked Well as a Team

### 1. Clear Primary Roles

The team established primary responsibility areas for backend development, database management, project coordination, frontend development, and integration testing.

This helped team members understand where they should focus their work.

### 2. Shared Project Goal

The team remained aligned around the central purpose of Asalah: helping Saudi families teach children responsibility, values, and basic financial awareness through tasks, Noor Points, wishlist goals, and rewards.

This shared goal made it easier to decide which features were essential.

### 3. Sprint-Based Progress

Weekly sprint goals gave the team a common focus and made progress easier to evaluate.

The sprint structure allowed the team to:

- Identify completed work.
- Record unfinished work.
- Review blockers.
- Plan corrections.
- Move incomplete tasks into the following sprint when necessary.

### 4. Frontend and Backend Collaboration

Frontend and backend members worked together during integration.

API documentation, Swagger testing, and Dio logs helped both sides identify:

- Incorrect payloads.
- Missing fields.
- Validation differences.
- Authentication problems.
- Unexpected response structures.
- State-refresh issues.

### 5. Knowledge Sharing

Team members supported one another when blockers appeared.

This included:

- Explaining API behavior.
- Reviewing validation rules.
- Checking database relationships.
- Testing complete workflows.
- Reviewing interface behavior.
- Helping identify bugs.

### 6. Use of GitHub

GitHub provided a shared source of truth for:

- Project code.
- Branches.
- Commits.
- Pull requests.
- Documentation.
- Version history.

This reduced the risk of losing work and made team contributions easier to review.

### 7. Scope Protection

The team postponed optional features when necessary so that the core MVP could be completed.

This helped protect the main parent-child workflow from unnecessary scope expansion.

### 8. Final Delivery

Despite technical and organizational challenges, the team successfully delivered:

- A working frontend.
- A working backend.
- A connected database.
- A functional parent experience.
- A functional child experience.
- Core task and approval workflows.
- Noor Points.
- Wishlist and reward features.
- Testing documentation.
- Production deployment.
- A landing page.
- A final presentation.
- A demonstration video.

## Main Team Challenges

### 1. Coordinating Frontend and Backend Timelines

Some frontend work depended on backend endpoints that were still being developed or updated.

This sometimes delayed integration or required frontend changes after API behavior changed.

#### Team Response

- Members communicated endpoint requirements.
- Swagger was used as a shared reference.
- Integration testing was repeated.
- Frontend payloads and backend responses were adjusted.

#### Retrospective Highlight

The team learned that frontend and backend work should be planned around agreed API contracts rather than developed independently.

---

### 2. Uneven Task Size

Some tasks were significantly larger or more complex than others.

A feature described as one task could include:

- Database changes.
- Backend logic.
- API endpoints.
- Frontend screens.
- State management.
- Validation.
- Testing.

#### Team Response

The team divided some large tasks during implementation and moved incomplete work when more time was needed.

#### Retrospective Highlight

Future tasks should be divided into smaller units with clearer acceptance criteria before a sprint begins.

---

### 3. Integration Bugs

The team encountered bugs involving:

- Request and response formats.
- Authentication tokens.
- Task statuses.
- Noor Points.
- Interface refresh behavior.
- Validation.
- Production configuration.

#### Team Response

- Team members reproduced the issues.
- Logs and API tools were reviewed.
- Fixes were tested manually.
- Regression checks were completed.

#### Retrospective Highlight

Integration testing should begin as soon as the first related frontend screen and backend endpoint are available.

---

### 4. Time Pressure Near Submission

Final bug fixing, documentation, testing, deployment checks, presentation preparation, and demo preparation occurred close to the deadline.

#### Team Response

- Critical workflows were prioritized.
- Optional enhancements were postponed.
- Team members focused on the most important remaining deliverables.
- The application was re-tested before final delivery.

#### Retrospective Highlight

A dedicated closure and stabilization period should be scheduled before the final submission date.

---

### 5. Keeping Documentation Synchronized

Technical and project decisions changed throughout development.

Some documentation required updates after implementation had already changed.

#### Team Response

- Stage reports were reviewed.
- Testing and deployment information was documented.
- Final deliverable links were collected.
- Stage 5 reports were prepared from the latest project information.

#### Retrospective Highlight

Documentation needs a clear owner and should be updated after every major change.

---

## What We Would Do Differently

In a future project, the team would:

- Assign a named owner to every feature.
- Assign a reviewer to every important feature.
- Define API contracts before frontend and backend work begin.
- Write acceptance criteria for every sprint task.
- Divide large features into smaller technical tasks.
- Begin integration testing during the first sprint.
- Use a structured GitHub Issues board.
- Record bug severity, owner, status, and verification result.
- Increase pull-request review before merging.
- Add more automated tests earlier.
- Keep documentation synchronized with implementation.
- Reserve more time for final interface consistency.
- Test more screen sizes and accessibility requirements.
- Prepare production test accounts earlier.
- Prepare the presentation and demo script before Stage 5.
- Reserve a complete stabilization period before final submission.
- Confirm names, roles, links, and deliverables across all project materials.
- Hold shorter but more frequent progress checks.
- Raise blockers earlier instead of waiting for the next major meeting.

## Communication Highlights

### Communication Methods That Worked

- WhatsApp was useful for quick questions and daily updates.
- Google Meet supported remote technical discussions.
- In-person meetings helped with planning and complex decisions.
- GitHub provided a permanent technical record.
- Sprint reviews helped the team compare completed work against planned work.

### Communication Improvements

Future communication could be improved by:

- Recording decisions in GitHub or shared documentation.
- Using fewer informal-only decisions.
- Adding short written summaries after meetings.
- Reporting blockers as soon as they appear.
- Using a shared task board with deadlines and owners.
- Confirming API changes with both frontend and backend members.

## Final Retrospective Summary

### Start

In future projects, the team should start:

- Writing API contracts before implementation.
- Assigning both owners and reviewers.
- Performing integration testing earlier.
- Recording decisions in shared documentation.
- Using a structured issue-tracking board.
- Preparing the final demo earlier.

### Continue

The team should continue:

- Using sprint goals.
- Communicating regularly.
- Supporting team members during blockers.
- Testing complete user workflows.
- Protecting the MVP scope.
- Using GitHub as the shared technical source of truth.

### Stop

The team should stop:

- Leaving integration until late in a sprint.
- Treating large features as single tasks.
- Delaying documentation updates.
- Leaving presentation and deployment preparation until the final days.
- Relying only on informal messages for important technical decisions.

## Conclusion

The Asalah team completed the project successfully and delivered the main planned MVP.

The strongest aspects of the team's work were:

- A shared product goal.
- Clear primary roles.
- Persistence during technical challenges.
- Collaboration during frontend-backend integration.
- Commitment to delivering the core workflow.
- Willingness to postpone optional features when necessary.

The main areas for improvement are:

- Earlier integration.
- Smaller task breakdown.
- Stronger task ownership.
- More structured issue tracking.
- Earlier automated testing.
- More time for stabilization and final preparation.

Overall, the project strengthened the team's technical, organizational, communication, and problem-solving skills and provided valuable experience that can be applied to future software projects.
